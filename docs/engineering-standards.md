# Engineering standards

Optimize for the next reader. Name concepts with the product vocabulary, include units for quantities, and give public contracts clear inputs, outcomes and invariants. Use strict TypeScript, ESM and `erasableSyntaxOnly` and validate external values with Zod. Reuse current domain rules and public package exports before creating new boundaries.

Keep one reason to change per module, put tightly related logic together and limit coupling. Keep policy independent of HTTP, ADK and storage. Inject effects such as external requests, clocks, providers and persistence at understandable seams. Prefer composition. Use SOLID principles when they serve the behavior, KISS for control flow, DRY for shared knowledge and YAGNI for speculative infrastructure. Add a pattern only for a real variation point or testability need. Choose boundaries by responsibility and readability rather than line counts.

Make asynchronous completion and failure explicit. Preserve inputs when ownership is shared, make state transitions predictable, and design retryable effects to be idempotent. Choose arrays for small ordered sequences, maps for repeated keyed lookup, and sets for membership or deduplication. Measure first before choosing heavier structures. Keep queues, concurrency, timeouts, retries and provider spend bounded. Pass cancellation to the underlying operation where supported and release resources on success and failure.

Classify expected operational errors separately from programming defects. Preserve causes internally and use stable, non-sensitive client-facing errors. Log useful operation and outcome fields, avoid duplicate logs and redact secrets, full prompts and identifying text. Prefer deterministic tests at meaningful boundaries with injected I/O and clocks. Reproduce one important failure per regression test. See [development](development.md) for the checks and [skills inventory](skills-inventory.md) for deeper implementation examples.

Derive independent tests from approved observable behavior. Assert public outcomes and invariants through real variation points and use synthetic fixtures. Separate failure to load a planned contract from a test that reaches behavior and demonstrates the gap. Keep supplementary tests discoverable alongside the protected set. Follow the [two-session workflow and test strategy](development.md#independent-test-first-sessions).
